# Kechuang Building：20 个 L3 Scenario 扩展执行方案

> 实现状态（2026-08-25）：20/20 已完成声明式 Spec、独立注册、共享 Oracle、动态
> 室外 Profile、Runtime 事件、时间检查点闭环和统一最终审计。20 个 Oracle DAG 为
> 58–173 步，中位数 91.5；完整仓库测试结果为 155 passed、1 skipped。真实模型批量
> 实验及 do-nothing/错误策略基线仍属于下一阶段，不与确定性 Oracle 验收混为一谈。

## 1. 决策结论

近期目标固定为：**构建 20 个独立注册、可运行、可验证的 Building L3 Scenario**。

该数量是后续 L2/L1 切分、技能提取、Controller 评测和真实模型实验的基础，不以
“约 20 个跨层级 Scenario”替代，也不因基础设施工作量而削减。

当前已有的房间预约、K1324 环境协调与人数阶梯、K1315 标准会议、K1316 标准研讨
主要属于 L1/L2 能力资产，继续保留和复用，但不直接计入 20 个 L3。只有经过扩展后
真正覆盖长周期、多阶段和跨阶段状态继承的场景，才能计为 L3。

## 2. 总体指导思想

### 2.1 顶层牵引、Spec 驱动、批量构建

先规划 20 个具有独立决策价值的 L3，再建设共享 Spec、生命周期 Builder、Agent
工作流和验证器。20 个 L3 共享基础设施，但不能只是更换名称、日期或单一数值。

```text
房间静态事实
+ 世界与季节 Profile
+ 标准运营生命周期
+ 人员/活动计划
+ 用户互动事件
+ 服务目标与资源约束
+ Agent 参考策略
+ 统一评价指标
= 可运行 L3
```

### 2.2 L3、L2、L1 的职责

| 层级 | 职责 |
|---|---|
| L3 | 对完整工作日、多活动日或多日运营结果负责 |
| L2 | 解决一个独立短闭环，如会前准备、换场或空气质量控制 |
| L1 | 最小复核后执行一个主要动作并确认结果 |

20 个 L3 必须先作为完整场景独立运行。L2/L1 在 L3 内部作为 episode/action 存在，
待 20 个 L3 稳定后，再从真实 trace 和状态快照中切出独立可运行场景。

### 2.3 标准化协议，不固定唯一工具序列

Building Agent 的标准协议为：

```text
Observe
-> Reconcile
-> Prioritize
-> Plan/Patch
-> Act
-> Wait
-> Verify
-> Commit
-> Monitor
```

评价关注业务、环境、资源和终态是否正确。除非存在必要因果关系，不要求 Agent 精确
复制 Oracle 的每次工具调用。

### 2.4 用户互动是正常事件流

预约创建、人数变化、时间修改、房间修改、设备需求变化、提前结束和舒适偏好属于
正常智慧建筑业务，不视为故障。Agent 必须支持局部重规划、旧承诺清理和计划恢复。

当前阶段仍不考虑设备故障、传感器掉线、网络中断、紧急事件和恶意操作。

## 3. L3 合格定义

一个场景只有同时满足以下条件，才能计入 20 个 L3：

1. 覆盖一个完整工作日、完整多活动日或合理的多日周期；
2. 至少包含 3 个可辨识的 L2 episode；
3. 至少包含一次跨阶段物理或业务状态继承；
4. 至少包含两次发生在不同阶段的关键决策；
5. 包含人员、日程或环境的时间演化；
6. 包含命令执行后的物理等待和复查；
7. 有明确业务终态、设备终态和时间终态；
8. 有独立 Primary Metrics，能区分正确策略、错误策略和 do-nothing；
9. 相比其他 L3，最优动作选择、顺序、资源分配或反馈策略存在真实差异；
10. Oracle 可独立运行，真实模型可获得不泄露答案的 briefing。

以下情况不能计为新 L3：

- 只改变日期或会议名称；
- 只把室外温度从 30°C 改成 31°C，但不改变合理策略；
- 只替换设备 ID 或房间 ID；
- 只有一场会议的固定长工具链，没有跨阶段决策；
- Oracle 是没有观测反馈的固定时间脚本；
- 与已有场景具有相同初始状态、约束、动作和主要指标。

## 4. 标准 L3 运营生命周期

共享生命周期包含以下阶段，具体 L3 可以选择或重复其中部分阶段：

| 阶段 | 世界过程 | Agent 责任 |
|---|---|---|
| 初始化 | 加载天气、房间、设备、预约和初始环境 | 建立当前状态 |
| 日程计划 | 查看全天活动和资源 | 形成 Agenda 与承诺 |
| 开放前 | 房间无人、距离活动尚早 | 判断预处理时机 |
| 预处理 | 环境和设备准备 | 控制、等待、复查 |
| 到达 | 人员分批进入 | 根据实际占用调整 |
| 活动运行 | 办公、研讨或会议 | 周期反馈和设备保障 |
| 转换 | 午间降载、换场、模式切换 | 继承状态并局部重规划 |
| 后续活动 | 第二场活动或多房间并行 | 协调资源和优先级 |
| 结束 | 人员离开、活动完成 | 释放预约并关闭设备 |
| 最终审计 | 空房恢复和全天汇总 | 清理遗留并验证指标 |

## 5. Spec 架构

```text
BuildingScenarioSpec
├── WorldProfile
├── BaselineOperationPlan
├── InteractionStream
├── ServicePolicy
├── ConstraintSpec
├── AgentPolicySpec
├── ReferencePolicy
└── EvaluationSpec
```

### 5.1 职责边界

| 组件 | 描述 |
|---|---|
| WorldProfile | 动态室外天气、开始/结束时间、初始环境和物理覆盖参数 |
| BaselineOperationPlan | 活动、预约、人员占用和生命周期时间线 |
| InteractionStream | 运行中才向 Agent 暴露的用户或占用事件 |
| ServicePolicy | 温湿度、CO2、PM2.5、舒适度和设备 readiness 目标 |
| ConstraintSpec | 容量、时间、能耗、功率、耗材和禁止行为 |
| AgentPolicySpec | 优先级、迟滞、冷却时间、重复抑制和终止上限 |
| ReferencePolicy | 专家参考状态机和 Oracle 策略 |
| EvaluationSpec | 业务、环境、能耗、互动响应和终态判定 |

核心原则：

```text
Spec 定义题目；
ReferencePolicy 定义参考解；
EvaluationSpec 定义成功；
Controller 负责运行时规划和响应。
```

房间容量、面积、设备和传感器等静态事实继续由 `fairy/configs/rooms/*.yaml`
管理，不在每个 Scenario Spec 中重复。

## 6. 20 个 L3 候选目录

下列目录是近期硬性目标。实现中可以调整名称和细节，但四个场景族各 5 个、总数
20 个的规模和覆盖要求不变。

### A. 季节与室外环境族（5 个）

#### L3-01 夏季高温高湿综合工作日

- K1324 正常办公、K1316 上午研讨、K1315 下午会议；
- 制冷、除湿、人数热负荷和无人预冷能耗权衡；
- 指标：有人舒适度、湿度违例、总能耗、无人能耗。

#### L3-02 冬季低温干燥综合工作日

- 三房间按日程使用；
- 供暖、加湿、CO2 新风和热损失权衡；
- 指标：温湿度、空气质量、供暖能耗、恢复时间。

#### L3-03 春秋过渡季低能耗运行日

- 室外条件大部分时间适宜；
- Agent 应减少不必要 HVAC，利用合理通风；
- 指标：舒适度相当条件下的能耗与设备动作数量。

#### L3-04 强日照下午峰值负荷日

- 上午环境平稳，下午太阳得热显著；
- 需要预判而非温度超标后持续振荡控制；
- 指标：下午峰值温度、达标时间、峰值功率和能耗。

#### L3-05 室外 PM2.5 偏高的活动日

- 多房间有人且需要控制 CO2；
- 新风会引入颗粒物，需要协调通风和净化；
- 指标：CO2/PM2.5 联合违例时长和净化/通风能耗。

### B. 空间、占用与活动结构族（5 个）

#### L3-06 K1324 分批到达与午间降载工作日

- 教师、共享隔间和研究生工位分批占用；
- 上午增载、午间降载、下午恢复和下班关闭；
- 指标：occupied-hour 舒适度、人数响应和无人能耗。

#### L3-07 K1316 连续两场研讨周转日

- 两场研讨间隔短；
- 第一场残留 CO2 和热负荷成为第二场初始状态；
- 指标：换场恢复时间、第二场会前达标率和额外能耗。

#### L3-08 K1315 多阶段答辩会议日

- 材料准备、报告、问答、闭门讨论和总结；
- 灯光、投影、音响、打印与环境模式多次切换；
- 指标：阶段 readiness、设备状态正确率和结束清理。

#### L3-09 K1315/K1316 同时会议协调日

- 正式会议和小型研讨同时运行；
- 两个房间的设备、环境和日程必须隔离；
- 指标：分房间舒适度、错误房间动作、并行完成率。

#### L3-10 三房间高占用综合运营日

- K1324、K1316、K1315 在重叠时段接近容量；
- 多 zone 同时反馈控制和全天收尾；
- 指标：全楼空气质量、总能耗、峰值负荷和最终清理。

### C. 用户互动与计划重构族（5 个）

#### L3-11 人数减少后的会议室降级调整日

- 原计划使用 K1315，人数减少后 K1316 足够；
- Agent 判断是否换房，并处理旧预约、已启动设备和新准备；
- 指标：意图满足、撤销完整性、额外能耗和准备及时性。

#### L3-12 人数增加后的会议室升级调整日

- 原计划 K1316，人数增加超过容量，需要迁移 K1315；
- 保留可复用任务，重建受影响部分；
- 指标：容量合规、计划污染范围和新房间 readiness。

#### L3-13 会议提前后的压缩准备日

- 用户将会议开始时间提前；
- Agent 在有限时间内调整打印、环境和设备准备优先级；
- 指标：关键服务准时率、非关键任务取舍和能耗。

#### L3-14 会议设备需求追加日

- 已预约活动运行前新增视频会议、麦克风或打印要求；
- Agent 保持原计划有效部分，只补充新增能力；
- 指标：局部重规划范围、重复动作和设备 readiness。

#### L3-15 活动提前结束与资源恢复日

- 一项活动正常提前结束，后续还有其他房间活动；
- Agent 关闭、释放并重新计算剩余全天计划；
- 指标：响应延迟、空房能耗、承诺一致性和后续活动稳定性。

### D. 资源约束与决策权衡族（5 个）

#### L3-16 全楼总功率受限的并行活动日

- 三房间同时有需求，但存在瞬时功率上限；
- Agent 必须错峰预处理并按优先级分配资源；
- 指标：功率越界、活动 readiness、舒适度和总能耗。

#### L3-17 严格无人能耗预算工作日

- 日程已知但活动间隔较长；
- Agent 需要选择合理预处理窗口而非持续运行；
- 指标：无人能耗、会前达标率和设备启动次数。

#### L3-18 多活动打印与材料协调日

- K1315/K1316 多场活动共享有限打印时间和耗材；
- Agent 安排批次、优先级和设备开关；
- 指标：材料按时完成率、耗材、打印机运行时间和任务顺序。

#### L3-19 冬季高占用下的新风—供暖权衡日

- 高人数导致 CO2 快速上升，室外低温造成显著通风热损失；
- Agent 需要采用反馈和维持策略；
- 指标：CO2 违例、温度违例、供暖能耗和控制振荡。

#### L3-20 多承诺优先级综合日

- K1324 长时办公、K1316 连续研讨、K1315 正式会议重叠；
- 准备时间、能耗和业务承诺同时受限，并包含一次正常计划修改；
- 指标：承诺满足率、优先级正确性、全楼稳定性和最终清理。

## 8. Agent 工作流要求

### 8.0 当前工作流实现口径

本轮对农业 full-season 场景和 Building L3 进行了对照审计。农业 L3 的 Oracle 通常为
214–383 步，中位数约 252，但其中包含逐日推进、田块级批量动作以及跨生育阶段操作。
Building 场景的状态变化更密集且设备控制粒度不同，不能用农业步数直接判定是否达到
L3。当前采用以下语义标准：

- 检查点覆盖占用、会议准备/开始/结束、互动、打印 deadline、小时巡检和日终审计；
- 关键设备动作之后必须推进物理时间并读取传感器复查；
- 状态未变化时不重复发送同一组命令；
- 清场时只关闭参考策略实际可能启动的设备；
- 步数由业务阶段和反馈闭环自然产生，不以末尾批量动作补足。

据此，20 个 Building L3 的 58–173 步均具有可解释节点。后续新增场景仍按闭环覆盖
验收，不设置脱离业务结构的统一绝对步数门槛。

### 8.1 分层计划

```text
L3 Agenda Manager
├── L2 Episode Controller
└── L1 Skill Executor
```

Agenda 保存全天计划、业务承诺和优先级；Episode 负责会前准备、环境控制、换场等
闭环；Skill 负责预约、打印、设备设置和状态确认。

### 8.2 结构化计划状态

Controller 至少维护：

- plan ID 和版本；
- goals 与 commitments；
- active/completed/cancelled episodes；
- 下一次唤醒时间；
- 当前设备控制模式；
- 稳定检查次数；
- 无改善次数；
- 已处理 interaction/event ID。

### 8.3 重规划规则

| 影响范围 | 响应 |
|---|---|
| 只读查询 | 回答后继续原计划 |
| 单一设备偏好 | 修补一个 L1 |
| 人数或设备需求变化 | 重建受影响 L2 |
| 房间、时间或资源冲突变化 | 重建剩余 L3 Agenda |

所有控制闭环必须有迟滞、冷却时间、重复命令抑制、最大迭代和明确终止条件。

## 10. 分阶段执行计划

### Phase 0：口径、审计与设计冻结

- 审计现有 5 个场景的实际层级和可复用 episode；
- 冻结 L3 合格定义和 20 项目录；
- 建立覆盖矩阵与 ID 命名规则；
- 输出 Spec schema 和 Agent 状态机设计。

验收：20 个候选均能说明独立决策、至少 3 个 L2、Primary Metrics 和不重复原因。

### Phase 1：Spec 与共享基础设施

- 实现 Spec 数据类型和静态校验；
- 实现动态 OutdoorProfile；
- 实现通用生命周期和 Runtime 事件安装；
- 实现统一 EvaluationSpec；
- 保持现有测试兼容。

验收：一个 Spec 可生成完整世界、时间线、Oracle 和验证结果。

### Phase 2：四个锚点 L3

优先实现 L3-01、L3-07、L3-11、L3-16，分别验证：

- 季节物理；
- 连续活动状态继承；
- 用户互动重规划；
- 跨房间资源约束。

验收：4/4 Oracle 成功，do-nothing 可区分，真实模型至少完成一次工程运行。

### Phase 3：扩展至 10 个 L3

- 完成每个场景族至少 2 个；
- 完善 Controller 的计划版本、局部修补和终止机制；
- 建立批量运行和结果汇总脚本。

验收：10/10 独立注册、Oracle 成功、无工具错误、覆盖矩阵达标。

### Phase 4：扩展至 20 个 L3

- 完成目录中剩余场景；
- 对相似场景做成对反事实检查；
- 删除仅换皮、不能改变最优策略的候选并以同族新候选替补；
- 运行完整 Oracle、do-nothing 和代表性真实模型实验。

验收：20/20 满足本文件第 3、7、11 节要求。未达到 20 个不得进入“L3 基础完成”状态。

### Phase 5：从 20 个 L3 切分 L2/L1

- 基于 fresh Oracle trace 审计真实 task atom；
- 导出完整 Building 状态快照；
- 实现独立 L2/L1；
- 开展技能库、检索和迁移实验。

L2/L1 的数量不能反向替代 Phase 4 的 20 个 L3。

## 11. 单个 L3 验收清单

- [ ] 独立 Scenario ID 已注册；
- [ ] Spec 静态校验通过；
- [ ] 时间线覆盖完整周期；
- [ ] 至少包含 3 个 L2 episode；
- [ ] 至少有两次跨阶段决策；
- [ ] Runtime 事件与工具工作流职责分离；
- [ ] 用户 briefing 不泄露未来事件或 Oracle 答案；
- [ ] 环境动作后存在等待和复查；
- [ ] Oracle 所有主要动作返回成功；
- [ ] do-nothing 或错误策略产生可区分指标；
- [ ] 最终预约、人员和活动状态正确；
- [ ] 最终无不应运行的设备；
- [ ] 有人舒适度和空气质量指标有效；
- [ ] 总能耗和无人能耗可统计；
- [ ] Controller 没有重复控制或无限振荡；
- [ ] 与已有 L3 的不重复理由已记录；
- [ ] 自动测试通过；
- [ ] 运行结果可由统一汇总脚本读取。

## 12. 统一评价指标

### 业务

- 活动完成率；
- 预约冲突和释放状态；
- 设备 readiness；
- 打印任务完成；
- 人员、房间和日程一致性。

### 环境

- occupied comfort violation seconds；
- air quality violation seconds；
- peak CO2 / PM2.5；
- minimum comfort score；
- 达标时间和稳定维持时间。

### 能耗

- 总能耗与分房间能耗；
- 无人能耗；
- 峰值功率；
- 单位 occupied-hour 能耗；
- 重规划额外能耗。

### Agent 与互动

- 工具调用数和重复命令数；
- Agent wake 次数；
- 最大控制迭代；
- 是否正确终止；
- 互动响应延迟；
- 用户意图满足率；
- 旧承诺清理完整性；
- 无关计划保持率；
- 被替代计划动作执行数。

## 13. Git 与交付边界

每个 Phase 独立提交，避免一次提交同时包含 Spec、Controller、物理引擎和 20 个场景。
每批提交必须附带：

- 新增 L3 表；
- 覆盖矩阵变化；
- Oracle/do-nothing 结果；
- 测试命令和结果；
- 已知限制；
- 下一批依赖。

临时运行报告继续保存在忽略目录；人工审核结论、场景目录和聚合指标进入版本控制。

## 14. Definition of Done

近期 Building L3 基础只有在以下条件全部满足时完成：

1. 20 个 L3 均独立注册并可运行；
2. 20 个 L3 均通过 Spec、Oracle 和自动验证；
3. 20 个 L3 均具有独立决策价值和不重复说明；
4. 四个场景族各有 5 个 L3；
5. 动态环境、占用活动、用户互动和资源权衡均达到覆盖硬指标；
6. Agent 能执行标准运营流，并对正常互动进行局部或全局重规划；
7. 所有场景均输出统一业务、环境、能耗和 Agent 指标；
8. 不以现有 L1/L2 或新切分的 L1/L2 折算 L3 数量；
9. 完成后方可将工作重心转向系统性 L2/L1 切分和技能迁移实验。

## 15. 当前实现后的下一阶段

确定性 Oracle 已满足时间推进、事件对账、设备动作、物理等待、传感复查和终态审计。
下一阶段依次进行：

1. 为 20 个场景建立 do-nothing 与代表性错误策略基线，验证指标确实可区分策略；
2. 在 Building 专用 Controller 中实现基于真实传感返回值的阈值、迟滞、冷却时间和
   最大反馈次数，而不是在静态 Oracle capture 阶段伪造动态分支；
3. 使用真实模型批量运行，并统计工具错误、重复动作、互动响应和终止行为；
4. 根据真实 trace 切分 L2/L1，避免仅依据 Oracle 源码预先制造原子技能。
