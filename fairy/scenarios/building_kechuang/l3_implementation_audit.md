# Building L3 实现审查记录

## 审查结论

20 个 L3 已具备可回放的完整时间线、共享闭环工作流和硬状态验收，但初版存在一些
“测试能通过、实验结论却不一定成立”的问题。本轮优先修复因果错误、空洞阈值和明显
物理不一致，没有用增加 DAG 节点或放宽验证掩盖问题。

## 已确认并修复的问题

| 问题 | 风险 | 修正 |
|---|---|---|
| 舒适违例比例上限为 1.0 | 100% 有人时段不舒适仍能通过 | 20 个 Spec 统一采用小于 1 的硬上限 |
| 冬季沿用房间 YAML 中的夏季初始室温 | 季节场景初态不可信 | Spec 显式定义季节初始温湿度 |
| 首批人员到达后才启动环境设备 | 把本可避免的超限算入正常策略 | 为每个房间增加首次占用前预处理检查点 |
| 所有会议固定提前 30 分钟准备 | 严寒/高温环境来不及恢复 | fan/cooling/heating 分别提前 30/60/90 分钟 |
| 低占用也强制开启专用新风 | 夏季增湿、冬季热损失过大 | 新风按占用比例分级，低负荷允许关闭 |
| 功率受限时把低优先级房间切为 fan | 功率达标但室温失控 | 保留制冷/供暖语义，只降低设备等级 |
| 通风空气没有热湿回收 | 严寒下设备能力与热损失不匹配 | 设备—物理接口加入显热/潜热回收，默认 0 保持兼容 |
| readiness 只检查设备是否曾开启 | 开会前已经关闭仍会误判成功 | 重放设备事件，验证会议开始时的最新电源状态 |
| 同一分钟先发布准备到期、后发布计划修改 | 结果事件先于原因事件 | 同时刻优先处理计划修改，再发布派生准备事件 |
| 打印机隐式并行、priority 未使用 | 材料协调场景没有资源竞争 | 单打印机串行排程，同刻任务按 priority 提交 |
| 打印验收依赖固定 job 序号 | 调整提交顺序后会错配材料 | 以 document name 与实际 job ID 验证 deadline |
| Spec 缺少边界校验 | 非法时间线可能到运行时才失败 | 校验负时间、周期越界、重复项、重叠会议和互动引用 |

## 当前结果

- 20/20 Oracle 回放并通过最终审计；
- DAG 节点数 58–173，中位数 91.5，均来自业务检查点和反馈闭环；
- 全仓库测试：155 passed、1 skipped；
- 本轮变更相关文件的 Ruff 检查与 `git diff --check` 通过；仓库全量 Ruff 仍有既存
  技术债，不在本轮 Building L3 修改边界内；
- 冬季综合场景 L3-02 的有人舒适违例比例由约 1.00 降至约 0.28；
- 冬季新风—供暖场景 L3-19 由约 1.00 降至约 0.20；
- L3-20 在保留制冷语义后峰值功率约 4.3 kW，低于 4.6 kW 限制。

上述数字是确定性模拟结果，不代表真实 K1315/K1316/K1324 的实测性能。

## 尚未解决的关键边界

1. Oracle 在 `capture_mode` 中是静态参考策略。传感器读取会验证真实物理演化，但不能
   根据尚未返回的读数动态改变 DAG；真正的条件分支仍应由 Building Controller 实现。
2. 当前舒适违例上限为统一工程阈值，热回收效率也是待标定参数。接入真实传感器后，
   必须用房间实测数据标定热容、围护结构、渗透率、设备能力和回收效率。
3. `primary_metrics` 中部分场景专属名称仍是研究指标声明，并未全部形成独立的一等
   计算字段。下一步需要建立指标注册表，禁止指标名称只有文本而没有 evaluator。
4. do-nothing 对照已用于人工审查，但尚未成为 20 个场景的自动化基线测试。仅验证
   Oracle 成功，仍不足以证明评价函数能稳定区分一般错误策略。
5. 打印排程目前是非抢占式：任务一旦接受就保留槽位。若后续要研究临时高优先级插单，
   需要增加可取消/重排队列和相应业务成本。

## 后续改进目标

优先级按以下顺序执行：

1. 建立统一 Metric Registry，为每个 `primary_metrics` 名称提供计算器、单位和方向；
2. 为 20 个 L3 自动运行 Oracle、do-nothing 和代表性错误策略，输出成对差值；
3. 实现 Building 专用 Controller 的阈值、迟滞、冷却和最大反馈次数；
4. 使用真实模型批量运行，检查未来信息泄漏、重复动作、重规划污染和错误终止；
5. 接入真实传感器 shadow 数据后进行参数标定，再收紧各场景 EvaluationSpec；
6. 从真实 trace 切分 L2/L1，而不是用固定 Oracle 工具链提前假定技能边界。
