## 4. 模型与 Controller 问题

### 4.1 时间推进不能在事件边界中断

`SystemApp.advance_time()` 可以一次跨过多个 Building Runtime 事件。Runtime 会更新
物理状态和占用，但不会中断当前 Agent 调用并强制重新规划。因此出现两种相反错误：

- L3-01、04、09、10、13、16、19、20 在最后一个外生事件前结束；
- L3-02、03、05、11 在最后事件后继续 8–15 小时。

L3-06 的独立 Smoke 曾因一次推进 4 小时漏掉 14 人返场而失败，本次采用不同推进路径
后通过，进一步说明结果对单次 ReAct 路径高度敏感。

### 4.2 缺少显式有限状态和终止判据

模型经常在“有人舒适控制”“会议收尾”“无人安全状态”之间来回切换。当前 Prompt 只
描述完整协议，没有机器可检查的阶段状态、下一关键事件和日终 deadline，导致固定时间
步重复观察。L3-13 达到 97 Tool / 98 LLM，接近 Controller 的 100 轮上限。

### 4.3 上下文成本不可接受

ReAct 每轮携带完整历史和 30 个 Tool schema。20 场累计超过 2,000 万 Token，单场
中位数接近 100 万。高频工具主要是 `advance_time`、传感器读取、当前时间和逐设备状态
查询。后续需要阶段摘要、结构化工作记忆和批量状态读取，不能只提高迭代上限。

### 4.4 参数约束仍会退化

共观察到 10 次明确拒绝或错误：

- 不存在的设备：`k1316_humidifier_01`、`k1324_lighting_01`、
  `k1316_purifier_01`；
- 非法级别：HVAC fan level 4，ventilation level 4 和 5；
- 时间错误：`advance_time(hours=-8)`、`advance_time(hours=0.5)`；
- 日期错误：`2026-09-018`；
- 关闭照明时提交非法色温 0 K。

模型通常能够从拒绝中恢复，但这些错误会扩大轨迹和 Token，并可能错过事件窗口。

### 4.5 最终自然语言报告并不可靠

L3-06 独立 Smoke 将实际空气净化器操作写成“加湿器辅助”。因此结果页面必须从
runtime trace 和 validator metadata 生成，不能直接展示模型自述作为实验事实。

## 5. Scenario、接口与 Validator 问题

### 5.1 打印目标对 Agent 不可见，但 Validator 严格检查

`print_batches` 的精确 `document_name`、copies、pages、submit time、deadline 和 priority
只存在于 Spec、Oracle workflow 和 Validator 中，未进入 `scenario_input`、日程或可查询
任务接口。真实 Agent 无法知道 `defense_materials`、`advanced_agenda`、
`hybrid_handout`、`seminar_notes` 等精确目标。

L3-18 根据会议标题自行构造了 `Materials_Seminar_Materials` 和
`Materials_Conference_Materials`，而 Validator 要求三个不同的固定批次，因此即使实际
打印完成仍必然失败。这是不可解/不公平的评测条件，必须先修 Scenario 信息通道。

### 5.2 交互场景存在未来信息泄漏和初态污染

交互类标题和研究问题直接说明“降级”“升级”“提前”“新增设备”，模型可在事件发生前
推断未来变化。L3-11、12 在 08:00 就取消旧会议并创建新会议，而交互事件应在 10:00
才发生。L3-12 的初始日程还直接包含最终的 14 人规模，使容量冲突提前可见。

应提供中性的日初任务，只在事件到点后通过通知暴露变化；初始 Schedule 必须使用真正
的旧房间、旧人数、旧时间和旧能力需求。

### 5.3 初始传感器读取为空

17 个场景首次调用 `read_all_sensors()` 得到空 readings，直到第一次物理推进后才有
观测。这迫使 Agent 在无环境基线时等待或先执行动作。Scenario 初始化后应立即生成一
组时间戳一致的初始观测。

### 5.4 通用失败信息粒度不足

当前失败 rationale 统一为 `one or more L3 lifecycle or cleanup invariants failed`。
metadata 虽包含各布尔量，但缺少：

- 具体哪个会议未完成、哪个预约未释放、哪个房间仍有多少人；
- 哪个打印批次缺失或晚了多少分钟；
- CO2、PM2.5、舒适度分别由哪个房间、哪个时间段造成；
- Agent 结束时距离下一关键事件还有多久。

这些信息应由 Validator 直接生成 failure reasons，减少人工扫描 JSONL。

### 5.5 约束场景的区分度需要重新审核

本轮所有场景的 `power_violation_seconds` 都为 0，所有适用的空房能耗预算都通过，但
L3-16、17 仍因其他指标失败。需要确认功率和空房预算是否足够紧，且不能通过提前结束
或少开设备投机满足。约束评测必须与有人舒适和活动完成联合判断。

## 6. 建议的优化顺序

1. 修复评测可解性：公开打印任务，清除交互未来泄漏，初始化传感器观测；
2. 让时间推进停在下一关键事件，返回 `interrupted_by` 和待处理事件摘要；
3. 为 Building Controller 增加显式阶段状态、下一事件、场景 deadline 和终止条件；
4. 增加 trace-grounded 结果生成器及细粒度 Validator failure reasons；
5. 引入阶段摘要、批量状态工具和重复动作检测，降低上下文成本；
6. 修复后先重复运行 L3-06、11、12、13、18、20，再进行 20 场全量回归；
7. 单次路径稳定后再使用多个随机种子，报告成功率而不是单次布尔结果。

本轮结果是工程诊断基线，不代表模型能力的最终统计结论。任何 Prompt、Controller、
Runtime 或 Scenario 修改都应在新的输出目录运行，并与本目录逐场对照。

## 7. 第一类问题修复后的分层复测

第一轮 Controller 修复加入运行边界、会议 readiness 和环境闭环接口，并对 Agent 最终
回答增加硬终止守卫。针对 L3-06、12、13、14、16、20 的复测结果为 4/6：L3-06、12、
13、14 通过；L3-16 只剩功率越界；L3-20 剩功率、会议准备和打印截止时间。产物位于
`runs/building_qwen36_35b_l3_repair_after_controller_fix_20260825/`。

第二轮增加两个公开控制契约：

- `get_commitment_status()` 将已公开会议和打印任务按截止时间统一排序；
- `get_power_budget_status()` 根据当前设备命令给出保守功率上界，超限时禁止继续等待。

L3-16 随后通过，峰值功率为 3857.47 W，越界时长由 10800 秒降为 0。L3-20 的功率、
三个会议 readiness 和打印 deadline 也全部通过，只剩 K1324 在仍有 10 人时被关闭通风，
模型收到空气质量事件后未纠正，最终 occupied peak CO2 为 1911.06 ppm。产物位于
`runs/building_qwen36_35b_l3_constraint_repair_20260825/`。

因此第三轮增加时间推进前环境协调守卫：有人时，Agent 必须在推进时间前读取环境状态；
设备变更或时间推进后必须重新协调；若某项环境指标已越界，则对应 HVAC、通风或净化
控制未启动时会拒绝继续推进。Oracle 使用 `stop_on_event=False`，不受此在线守卫影响。

最终 L3-20 在线复测中，新守卫已实际拒绝未经环境协调的时间推进，且挂起前打印、会议
准备和功率闭环均按新契约执行。但远端模型在 14:00 的请求长期无响应，运行被人工终止，
没有生成最终 Validation，故该次结果应标为“网络/服务中断，未判定”，不能计为通过或
失败。进度保存在 `runs/building_qwen36_35b_l3_environment_guard_20260825/`。

当前结论应严格区分：修复目标集已有 5 个场景获得完成态通过（L3-06、12、13、14、16）；
L3-20 的旧三项失败已消除，但新增环境守卫仍需一次不中断的完整在线复测。尚未重新运行
全部 20 场，因此不能宣称 20 场整体成功率已经更新。

## 8. L3-20 环境守卫重试结果

模型服务恢复后，在
`runs/building_qwen36_35b_l3_environment_guard_retry_20260825/` 完成了一次有最终报告的
重试。该次运行未通过，停止原因为 `max_tool_calls`：180 次 Tool、180 次 LLM、
6,635,685 Token，仿真只推进到本地时间 11:46。

这次结果不是原环境问题的重复：occupied peak CO2 已降至 714.26 ppm，峰值功率为
3869.96 W 且越界时长为 0，打印任务也在 deadline 前准确完成。失败发生在流程预算：
时间推进前环境守卫共拒绝 30 次，其中 29 次为 `environment_reconciliation_required`，
1 次为 `occupied_environment_uncontrolled`。高频 Tool 为 `advance_time` 58 次、
`get_environment_control_status` 36 次。模型在“控制变更—环境复核—短步推进”中消耗了
过多轮次，未等到后续交互、正式会议和日终事件。

因此本轮暴露的是新的 Controller 协议粒度问题：环境守卫保证了安全性，但把每次设备
变更和每次推进都变成独立握手，产生过高协调成本。下一步不应简单提高 Tool 上限，而应
将“检查环境 + 提交一组控制 + 验证功率 + 安全推进至下一个检查点”合并为有状态的批量
控制事务，或让 `advance_time` 返回可恢复的 reconciliation token，避免对同一状态重复
拒绝。完成该优化前不启动 20 场全量回归。

## 9. 放宽调用预算后的 L3-20 正确性验证
