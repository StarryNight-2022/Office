# Building L3→L1 业务能力拆分标准

版本：v1.2，2026-09-12。适用：`l3/catalog.py` 中的 20 个 Building L3。

## 1. 最新定义

Building 采用两层：L3 是完整工作日内多项承诺的组织、排序、资源协调和持续运行；L1 是可在不同地点、时间和状态下复用的一项完整业务能力。

**L1 = 同一业务目标或同一主 object + 完成该目标所必需的观察、判断、操作、等待与结果确认。**

L1 的身份不由一次执行实例决定。下面这些差异默认只是同一 L1 的输入或测试变体：

- 执行时间、日期、房间和具体设备 ID；
- 设备原来关闭、已经开启或处于其它合法状态；
- 目标温度、风量、亮度、色温、音量、输入源、打印数量等参数；
- 空队列或忙队列、有无房间冲突、不同背景负载；
- 同一流程中因条件判断产生的合法分支；
- 同一 L3 或不同 L3 中重复出现的同类需求。

例如，把关闭的空调开启并设为 24°C，与把已经运行的空调从 26°C 调到 23°C，都是“空调控制”。其固定闭环是“温控需求 → 空调/现态检查 → 调节 → 查询确认”；初态和目标值不同，不产生两个 L1。若业务要求确认室温已经物理稳定，则在同一个空调控制能力的相应变体中增加等待、传感器复测和稳定判据，不另造“空调启动”和“温度调节”两个能力。

同理，照明需求的亮度、色温、场景和灯组会变化，但“照明需求 → 灯组/现态检查 → 开灯或调整 → 查询确认”只定义一个“照明控制”L1。

## 2. 能力身份与执行变体

每个正式 L1 由两部分组成：

1. **能力合同**：稳定的业务身份、主对象、流程骨架和成功判据类型；正式目录只为它生成一个 Scenario ID。
2. **来源变体**：来自 20 个 L3 的具体时间、房间、初态、参数、队列、约束和动作证据；全部保存在 manifest 和审计账本中。

归并来源变体不等于删除覆盖。每个候选、源写动作和业务义务仍必须映射到一个能力，或明确保留为 L3 触发/聚合验收。训练或测试需要更多状态组合时，应给能力增加 case/fixture，而不是复制新的 L1 身份。

## 3. 何时拆成不同 L1

只有出现以下至少一项本质差异才拆开：

- **业务目标不同**：例如“控制空调”与“创建会议室预约”；
- **主对象或对象集合的业务含义不同**：例如投影仪与音频系统分别可独立交付；
- **成功判据类型不同**：例如设备配置确认与会议/资源事务一致性；
- **不可分的共享约束不同**：例如需要跨房间联合决策的功率预算，不能退化为某一台设备的单独控制；
- **一个结果可在另一个结果完全失败时仍独立交付**，且上层 L3 确实需要分别组合它们。

以下理由不能单独用于拆分：时间不同、房间不同、设备当前状态不同、参数不同、用户人数不同、打印材料不同、检查点不同、同一动作是否刚好为 no-op、来自不同 L3。

## 4. 单 object 控制规则

能通过控制一种物品完成的任务，直接归为该 object 的一个 L1：

| 正式能力 | 固定闭环 | 变化输入示例 |
|---|---|---|
| 空调控制 | 温控需求 → 设备/现态检查 → 调节开关、模式、设温和风量 → 查询/必要时物理复测 → 确认 | 房间、初温、是否已开、目标温度、冷热模式 |
| 新风控制 | 空气需求 → 新风机/现态检查 → 开关或档位调整 → 查询确认 | CO₂ 背景、开关、档位 |
| 加湿器控制 | 湿度需求 → 加湿器/水位/现态检查 → 调节 → 查询确认 | 初始湿度、水位、开关、档位 |
| 空气净化器控制 | 空气质量需求 → 净化器/滤芯/现态检查 → 调节 → 查询确认 | PM2.5 背景、滤芯、开关、档位 |
| 照明控制 | 照明需求 → 灯或灯组/现态检查 → 开灯或调整 → 查询确认 | 灯组、亮度、色温、场景 |
| 投影仪控制 | 演示需求 → 投影仪/现态检查 → 开关或输入源调整 → 查询确认 | 设备、开关、输入源 |
| 音频系统控制 | 扩声需求 → 音频/现态检查 → 音量和麦克风调整 → 查询确认 | 音量、麦克风、初始状态 |
| 打印机控制与交付 | 公开需求 → 打印机/队列/时限检查 → 必要时开机 → 提交 → 等待 → 对应作业查询确认 | 文档、数量、优先级、deadline、队列 |

一次会议准备可能同时需要空调、灯、投影和音频；若这些结果可分别验收，它们是 L3 中组合的四种 L1 能力，不因共同出现在“会议准备”阶段就复制四套场景，也不额外重复计算一个包含全部子任务的叶子 L1。

## 5. 非单 object 的完整业务闭环

不能简单归结为控制一个物品的任务，只要围绕一个稳定业务目标形成端到端闭环，也定义为一个 L1：

| 正式能力 | 固定闭环 | 变化输入示例 |
|---|---|---|
| 会议室预约 | 需求 → 人员在场/日程/房间冲突检查 → 选房 → 创建会议与预约 → 查询确认 | 人员、时间、人数、房间偏好、设备需求、冲突 |
| 会议需求变更 | 用户变更 → 权限与当前承诺检查 → 取消/释放或修订 → 必要时重建承诺 → 会议与资源查询确认 | 人数增减、提前/延后、换房、追加设备 |
| 会议结束后的房间恢复 | 结束/空闲事实 → 后续承诺检查 → 回收或降载 → 房间、设备与承诺复核 | 结束时间、继承状态、后续预约、恢复配置 |
| 共享功率约束下的服务调整 | 多房间需求/已有负载 → 预算检查 → 联合控制 → 功率与服务复核 | 功率上限、房间集合、背景负载、设备组合 |

房间恢复不等于固定“全部关机”：连续会议可能要求维持通风或预处理。需求变更也不因“人数减少”“人数增加”“会议提前”“新增投影”而拆成四个 L1；这些都是同一变更能力的输入和分支。

## 6. 起点、终点与因果完整性

起点选择任务已经可见、尚未完成、核心决策未替 Agent 做掉的最早时刻。终点必须在业务结果被实际查询和核验之后。

- 查询、开关机、主动作、等待、通知处理和确认属于同一闭环，不能按工具或检查点拆开。
- 打印跨越多个检查点才完成，仍是一个打印机控制与交付 L1。
- 空调从关闭变为运行与从一个设温改为另一个设温，起点不同但能力相同。
- 命令成功不自动等于物理目标达标；声称温度、湿度或空气质量达标时必须保留物理推进、传感器复测和明确阈值。
- 预约/变更必须验证会议与 active reservation 的一致性，并保证其它承诺未损坏。
- 每个能力至少有一个独立代表夹具；不同变体可使用额外夹具验证，但不生成新的能力 ID。

## 7. 来源、Agent 责任与环境责任

源 L3 中的占用变化、会议开始/结束事件、天气变化和需求发布通常是触发或环境事实，不是 Agent 成绩。它们仍应保存在义务账本中，但不单独生成 L1。

当前 20 个 L3 在初始化时预置会议/预约，并由运行时自动应用部分日程变化。业务分类仍应包含“会议室预约”和“会议需求变更”两个 L1 能力；实现证据使用现有独立夹具和真实 `ScheduleApp`、`RoomApp`、`ResourceAllocationApp` 工具，manifest 必须明确标注为补充运行证据，不能伪称源 L3 Oracle 已执行这些动作。

打印需求由场景/用户事件公开，Agent 读取需求并控制打印机、提交作业、等待和确认。日终关闭共享打印机也归入同一打印机能力的来源变体，不另凑一个 L1。

## 8. 审计和 manifest 规则

1. 读取全部 20 个 L3 的业务义务、候选、Oracle 写动作和公共收尾动作。
2. 每个 L3 只顺序回放一次，在候选边界记录真实状态与动作是否改变状态。
3. 先按业务上下文识别会后恢复、共享功率和打印等不可拆业务闭环；其余设备动作按 object 类型映射。
4. 每个源写动作只能映射到一个能力。no-op 重申仍是同一能力的状态变体，不再生成或排除一个新的 L1 身份。
5. 每个业务义务映射到一个或多个能力，或标记为 `l3_context_trigger`、`l3_evaluation_objective`、`satisfied_by_existing_capability_state`。
6. 为每个能力选择一个有真实状态变化的代表实例构建独立 Oracle；所有其它来源保存为 `coverage.source_variants`。
7. 正式生成器只根据 manifest 中的 12 个 accepted capability 生成模块；旧的来源实例模块只有在带生成标记时才允许显式 `--prune`。

manifest v2 的关键结构：

```yaml
scenario_id: scenario_building_kechuang_l1_hvac_control
behavior_family: hvac_control
capability_kind: object_control
source:
  kind: diagnostic_representative
  l3_scenario_id: ...
  candidate_id: ...
  action_ids: [...]
coverage:
  identity_rule: same_business_goal_and_primary_object
  varied_dimensions: [设备, 房间, 时间, 初始状态, 目标温度, 风量]
  source_l3_ids: [...]
  source_variants: [...]
  obligation_refs: [...]
task: {goal: ..., prompt: ..., completion_report: ...}
initial_state: {...}
oracle_steps: [...]
validation: {...}
```

## 9. 当前 20 个 L3 的正式结果

252 个诊断候选不再一一变成场景。它们按能力身份归并为 **12 个正式 L1**：

- 单 object：空调、新风、加湿器、空气净化器、照明、投影仪、音频系统、打印机；
- 业务闭环：会议室预约、会议需求变更、会议结束后的房间恢复、共享功率约束下的服务调整。

711 个候选内源写动作与 5 个公共打印机收尾动作全部映射到唯一能力。389 条业务义务全部有去向：由能力覆盖、作为 L3 触发，或由既有能力状态满足。时间、房间、初态、参数、轮次和执行阶段只保留为覆盖变体。

完整机器证据：

- `l1/manifest.json`：12 个能力合同、代表夹具与全部来源变体；
- `workflow_exports/building_l3_to_l1_formal/review_ledger.json`：252 个候选和 716 个源动作的能力映射；
- `workflow_exports/building_l3_to_l1_formal/obligation_ledger.json`：389 条业务义务的去向；
- `workflow_exports/building_l3_to_l1_formal/generation_report.json`：12 个模块的编译、注册和 Oracle 回放结果。

## 10. 重建与验证

```powershell
python scripts/finalize_building_l1_review.py          # 预览能力归并
python scripts/finalize_building_l1_review.py --apply  # 写 manifest 与账本
python scripts/generate_building_l1_scenarios.py --force --prune --validate `
  --report workflow_exports/building_l3_to_l1_formal/generation_report.json
python -m unittest tests.test_building_l1_generation -v
python -m unittest tests.test_building_l1_diagnostic -v
```

验收必须同时覆盖：manifest/来源链接、能力 ID 唯一性、所有来源动作只归属一个能力、fresh-instance Oracle、do-nothing、漏关键动作、漏动作后确认、预约/变更事务一致性，以及没有残留旧生成模块。
