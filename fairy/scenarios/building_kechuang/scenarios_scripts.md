# Kechuang Building Scenario 描述与分层模板

本文件用于先由领域人员描述真实建筑业务，再由开发者将其细化为可运行 Scenario。
填写时不需要写 Python、设备 ID、App 名称、API 或 Oracle 答案；只描述现实中可见的
人员、空间、时间、环境、资源、约束和期望结果。

## 0. L1 / L2 / L3 口径

层级表示任务范围和决策闭环，不表示单纯的难度或工具调用数量。

| 层级 | 含义 | 典型结构 | Building 示例 |
|---|---|---|---|
| L1 | 单动作或单决策窗口 | 最小复核 -> 单一动作 -> 结果确认 | 预约房间、打印材料、调高通风、关闭会议设备 |
| L2 | 可独立验证的短业务闭环 | 观察 -> 判断/诊断 -> 必要等待 -> 行动 -> 复查 | 会前准备、CO2 控制、连续会议换场、办公室环境协调 |
| L3 | 多个 L2 连续构成的长周期综合任务 | 多阶段感知、决策、执行和反馈 | 完整工作日、多会议日或一周空间运营 |

判定问题：这个任务是在执行一个明确动作（L1）、解决一个阶段性问题（L2），还是
对多个相互影响的阶段及其最终结果负责（L3）？

建议先填写一份 L3 主场景，再从其时间线审计并填写若干 L2 和 L1。不要为凑数量
重复拆分；每个子场景必须有不同的初始状态、决策、动作、约束或主要评价指标。

|---|---|---|---|---|---|---|---|---|
| T01 |  |  |  |  |  | L1/L2 |  |  |
| T02 |  |  |  |  |  | L1/L2 |  |  |

接受条件：能够说明独立决策是什么、做对做错体现在哪个指标上，并且不只是改名称。

拒绝条件示例：没有动作、没有独立指标、已被另一个 task atom 完整覆盖，或者仅是
连续时间记录点。若以“重复”为由拒绝，应注明与哪个已有 Scenario 的初始状态、动作、
约束和指标相同。

|---|---|---|---|---|---|---|---|---|---|

建议整体至少覆盖：

- 房间选择与预约；
- 人员到达、离开与位置变化；
- 温度、湿度、CO2、PM2.5 反馈；
- HVAC、通风、净化、加湿和照明；
- 投影、音响、视频会议和打印；
- 单房间与多房间运行；
- 准备、活动、换场、收尾等生命周期；
- 舒适度、空气质量、时间和能耗之间的权衡；
- 达标后及时终止，避免重复观测和振荡控制。
