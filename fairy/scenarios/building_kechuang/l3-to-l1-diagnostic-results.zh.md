共 13 项业务原型：12 项满足所声明的局部对照要求，1 项暴露温度达标问题。这里包含一项预约补充夹具、一项空调启动替代合同，不能把 13 项都计为从 L3 提取出的新叶子场景。

### 温控反例对标准的反馈

L3-06 首次预处理从约 27°C 开始。每隔 5 分钟采样，温度约为：

```text
26.71 → 26.46 → 26.24 → 26.06 → 25.90 → 25.76 °C
```

设备指令和配置均正确，但末两次读数未进入试验合同的 21–25°C 范围，因此该温度准备合同未通过。标准据此明确区分：

- “启动空调并设置要求参数”：可在设备运行配置确认后完成。
- “使温度达到目标”：需保留实际物理响应与达标证据；不能在同一个位置提前结束。

30 分钟不是通用限制，21–25°C 也不是所有任务必须使用的阈值。后续若选择温度准备作为正式任务，需要结合源时限校准响应窗口/参考控制策略，或明确源任务可实现的目标，不能仅为通过试验而放宽阈值。修改策略后仍须保留反例并重新验证。

### 预约来源的限制

当前 20 个 L3 在 `initiate_scenario()` 中预置会议和预约，Oracle 不执行 `ScheduleApp.create_meeting()`。互动处理器还会自动应用部分会议/预约变更。因此，本轮没有声称从这 20 个 L3 中提取出自主预约或自主换房行为。

已有 `scenario_building_kechuang_room_booking` 提供真实预约工具路径，所以用它验证“需求/冲突检查 → 选房 → 创建 → 核验”标准。如果要把预约作为这 20 个 L3 的组成行为，需要先把相应预置事实转化为公开业务需求及 Agent 执行责任；这属于源 L3 设计调整，本轮未实施。

## 运行与复查

```powershell
python scripts/diagnose_building_l3_to_l1.py --probe-printing --probe-behaviors --force
python -m unittest discover -s tests -p test_building_l1_diagnostic.py -v
```

第一条命令因为温度准备原型未通过，当前预期退出码为 **1**，同时保存完整报告。第二条命令的 **8 个回归测试全部通过**，其中一个测试专门检查“空调配置成功但温度未达标”不会被误判为成功。两种结果含义不同。

机器证据位于：

- [`workflow_exports/building_l3_to_l1_diagnostic/README.md`](../../../workflow_exports/building_l3_to_l1_diagnostic/README.md)：20 个 L3 汇总及逐场报告入口。
- [`printing_probes.json`](../../../workflow_exports/building_l3_to_l1_diagnostic/printing_probes.json)：各轮打印的独立分支、队列与完整工具返回。
- [`behavior_probes.json`](../../../workflow_exports/building_l3_to_l1_diagnostic/behavior_probes.json)：预约、设备、温控与功率原型的合同、条件和完整工具返回。

本轮使用内存完整状态分支与确定性时间推进。源前缀仅用于离线获取初态，独立分支不继续执行其余 L3 Oracle。尚未验证磁盘存档、原生 L1 注册、真实 Agent 事件中断和所有跨任务/长期约束；不能将原型结果替代最终场景验收。

## 对正式能力归并的结论

这些诊断片段只负责保留来源证据。正式层已经进一步按业务能力归并：空调、灯、投影仪等
单 object 控制各自只保留一个 L1；预约、需求变更、会后恢复和共享功率调整各自按完整闭环
保留一个 L1。动作归属率和候选数量只用于查漏，不再决定正式 L1 数量。
